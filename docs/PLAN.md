# Gingerbread Biome Mod — Full Plan

Nov 17, 2026 · @Mental

## Concept and scope

Gingerbread Grove (working title) is a candy-and-cookie dimension with one hand-built biome, five original mobs and two lootable structures, shipped for 1.21.1 first and 26.3 second, on Fabric and NeoForge.

**The pitch.** You craft a Snow Globe, use it, and arrive in a frosted, sugar-sweet forest: gingerbread cliffs, candy-cane trees, icing snowdrifts, gumdrop bushes. The mobs are cookie and candy creatures, some hostile, some tameable. You raid gingerbread houses for loot and carry gifts home.

**Why a dimension, not an Overworld biome.** A dimension needs only data files (JSON) and no worldgen library, so it works the same on both loaders and cannot clash with other biome mods. Injecting the biome into the Overworld is a v1.1 option, once a library such as TerraBlender is confirmed for the versions you target.

**Ships in v1.0**

- 1 dimension, 1 biome (plus a lighter "frosted flats" edge variant if time allows)
- About 45 blocks, most of them stairs, slabs, walls and plank-style sets generated by datagen
- 5 entities (see Custom entities)
- 2 structures: a gingerbread house and a candy-cane outpost
- A Snow Globe item as the way in, plus 4 foods and a handful of tools and armor
- English and Bulgarian translations, EN first

**Not in v1.0:** a boss, a real portal block, Overworld spawning, custom music, an in-game config screen. These are v1.1 candidates and keep the first release finishable by December 5.

**Done means:** a player can craft the globe, travel, survive and fight, loot a house, and return, on both loaders without crashes in a 30-minute test world.

## Minecraft versions and loaders

Cover two versions, 1.21.1 first and 26.3 second, each on Fabric and NeoForge: four jars in total, and nothing in between.

Mojang dropped the 1.x numbering in December 2025 and now names versions by year and drop. Java Edition 26.3 ("Wilderness Bound") is the current release, out September 15, 2026, and the 26.x line needs Java 25 while 1.21.x runs on Java 21 ([Fabric 26.3 post](https://fabricmc.net/2026/09/15/263.html), [NeoForge 26.1 post](https://neoforged.net/news/26.1release/)).

| Target | Java | Fabric | NeoForge | Why | Ship by |
| --- | --- | --- | --- | --- | --- |
| 1.21.1 | 21 | Loader + Fabric API for 1.21.1 | 21.1.x | Largest modded audience: NeoForge's own review calls it the most popular version, with 16,000+ mods | Dec 5 |
| 26.3 | 25 | Loom 1.17, Gradle 9.6.0, Loader 0.19.5 | 26.3.0.x | Current release; shows up under the latest-version filter on CurseForge and Modrinth | Dec 12 |
| 26.1, 26.2, 1.21.2 to 1.21.11 | n/a | skip | skip | Players on these either stay on 1.21.1 or move to 26.3 | not built |

**Why 1.21.1 first.** Tooling is mature and most modpacks and servers still run it ([NeoForge 2025 review](https://neoforged.net/news/2025-retrospection/)). It is also the safer place to get the dimension, entities and loot working before porting.

**Why the port is real work, not a version bump.** The Fabric post says 26.3's changes are mostly about rendering, and several worldgen formats changed: configured features moved to a new data folder, the `config` object is gone from feature JSON, and surface rules became material rules. Entity renderers and worldgen JSON will therefore need a second copy for 26.3, so budget a full week.

**Forge.** NeoForge is the loader most 1.21+ modders and modpacks use. Forge itself exists for 1.21.1 (the 52.x line); I have not confirmed Forge support for 26.x, so check before promising it. If you want a literal Forge jar, make it a stretch goal for 1.21.1 only.

**Support policy after launch.** Bug fixes go to both versions. New content in v1.1 lands on both. Other versions only get a backport if there are real requests, and 1.21.1 is dropped once downloads for it fade.

## The Gingerbread biome

The biome is built almost entirely from data files and a small set of new blocks, so most of the work is design and datagen rather than Java.

**Look and feel.** Warm cream sky, light snowfall, pink-white fog, and cocoa-brown water. The water is vanilla water with a brown biome water colour, so there is no custom fluid code to port between loaders.

**Terrain.** Rolling frosted hills, with "cookie mesa" plateaus and gingerbread cliffs as the landmark shapes. This comes from a custom noise settings file and a surface rule: icing on top, gingerbread underneath, peppermint stone deeper down.

| Block family | Examples | Role |
| --- | --- | --- |
| Ground | Frosting, Frosted Gingerbread, Gingerbread, Peppermint Stone | Surface and cliffs |
| Trees | Candy Cane Log, Gumdrop Leaves, sapling, planks set | Tree features, building wood |
| Plants | Gumdrop Bush, Lollipop Flower, Sugar Grass | Ground cover, food source |
| Ores | Sugar Crystal Ore, Cinnamon Ore | Tool and armor materials |
| Building | Icing Bricks, Cookie Tiles, Candy Glass, Wreath, Lights | Decorative sets, mostly generated stairs, slabs and walls |
| Functional | Snow Globe (item), Gift Box, Cookie Jar | Entry, loot, storage |

**Structures.** Two, both stored as structure files and placed through jigsaw pools:

- Gingerbread House: a lootable house with a chest, a cocoa kettle and a guard mob inside
- Candy Cane Outpost: a tower with better loot and a small group of hostile mobs; this is the hook for a v1.1 boss

**Worldgen pipeline.** One datagen run writes the dimension type, dimension, noise settings, biome, features, structure sets and loot tables. Because 26.3 changed several of these formats, keep generation code per target version and share only the design values (colours, block lists, loot weights).

**Risks to test early.** Cliffs that cut off the surface rule, trees floating on plateau edges, structures buried in hills, and cave carvers opening the roof of a mesa. Start a test world in week 1 and fly around it before adding any entity.

## Custom entities

Five original mobs: three friendly, two hostile, so the biome feels festive first and dangerous second. Health values are starting points to tune in playtesting.

| Entity | Type | Behaviour | Health | Drops or trades | Effort |
| --- | --- | --- | --- | --- | --- |
| Gingerbread Man | Passive | Wanders, runs from players, leaves crumb particles; catching one is the game | 8 | Gingerbread Cookie, rare Gingerbread Heart | S |
| Cookie Soldier | Hostile | Patrols outposts, melee with a candy-cane spear, raises a cookie shield when hit | 24 | Cinnamon, Candy Cane | M |
| Gumdrop Blob | Hostile | Bounces toward players, splits into smaller blobs when killed, four colour variants | 16 | Gumdrops, Sugar | M |
| Peppermint Pup | Tameable | Tamed with a Candy Cane; follows, sits, defends its owner | 20 | None; wears a collar colour when tamed | L |
| Elf Trader | Trader | Lives in Gingerbread Houses; trades gifts and building blocks for Sugar Crystals | 20 | Trades: Wreaths, Lights, Gift Boxes | L |

**What each entity needs.** An entity class and attributes, a goal list for its behaviour, a model, a renderer and a texture, a spawn egg, a spawn rule in the biome file, a loot table, sound events and translations. The spawn rule and the loot table are plain data, so they cost almost nothing.

**Models and animation.** Build models in Blockbench and export them in the vanilla style, with simple code-driven animation (walk swing, head look, a bounce for the blob). Do not depend on an animation library in v1.0: 26.3 changed rendering heavily, and I could not confirm that GeckoLib has a 26.3 build. Revisit it for v1.1 if one appears.

**Build order.** Gingerbread Man first, because it is the simplest and proves the whole pipeline end to end on both loaders. Then Cookie Soldier, Gumdrop Blob, Peppermint Pup, and the Elf Trader last, since its trade screen is the most fiddly.

**Sounds.** Reuse and pitch-shift vanilla sounds for v1.0 and note it in the changelog; original audio can wait for v1.1.

**Stretch goal.** A Sugar Sprite: a small flying ambient mob that drops Sugar Crystals and lights up at night. Only add it if everything above is already stable.

## Technical architecture

Use one multiloader project with a shared `common` module and thin `fabric` and `neoforge` modules, so about 90% of the code is written once. Build the 1.21.1 and 26.3 versions as two branches of the same repository.

```text
gingerbread-grove/
  common/      blocks, items, entities, goals, worldgen design, datagen providers
  fabric/      entrypoint, registry glue, Fabric datagen runner
  neoforge/    mod class, registry glue, NeoForge datagen runner
  branches/    main = 1.21.1 (Java 21), mc-26.3 (Java 25)
```

**Rules that keep it portable**

- Write game logic against Mojang's own class names in `common`, and keep every loader call behind a small interface that each loader module implements (registration, creative tab, spawn placement, biome spawns).
- Make as much as possible data-driven: biome spawns, loot tables, recipes, tags, structure pools. Data files are identical across loaders.
- Generate blocks, models, lang files, recipes and loot with datagen, so adding the 40th block costs one line.
- Pin tool versions per branch. For 26.3 that means Java 25, Fabric Loom 1.17 and Gradle 9.6.0, as the Fabric team recommends; for NeoForge use its current ModDevGradle and confirm the 26.3.0.x build on neoforged.net.
- Keep Fabric API as the only required dependency on Fabric. Add no other libraries in v1.0.

**Testing.** Run both loaders against the same test world, and test a dedicated server, not just singleplayer: a missing `@Environment` or sided-class mistake only shows on a server. Keep a short manual checklist: craft the globe, travel, spawn each mob, loot a house, die and return, save and reload.

**Repository and CI.** Put the project on GitHub and use GitHub Actions to build all jars on every push; the same workflow can publish to CurseForge and Modrinth when you tag a release.

## Art, audio and what Claude can do

Claude can write nearly all the code, data and text for this mod, but it cannot compile or run Minecraft from its own workspace: I tested, and Fabric, NeoForge, Maven Central and Mojang's servers are all blocked there. Builds and playtests have to happen on your PC or in GitHub Actions.

No Minecraft-specific MCP server is connected to this session. The connected image and 3D generation tools (Higgsfield) are useful for promo art, not for in-game textures.

| Task | Claude | You |
| --- | --- | --- |
| Java: blocks, items, entities, goals, spawn and loader glue | Writes it, reviews errors you paste back | Build, run, report crashes |
| Worldgen, loot, recipes, tags, structure pools (JSON) | Writes and validates the files | Fly around the test world and judge the look |
| Datagen providers | Writes them | Run the datagen task |
| Structure files (houses, outpost) | Generates them with a script, block by block | Walk through, adjust, resave in-game |
| 16x16 block and item textures | Generates base textures with a script and a fixed palette | Polish in Aseprite or Blockbench |
| Entity models | Writes Blockbench model files from a layout spec | Open, tweak, export |
| Promo art: icon, banner, key art, short trailer clip | Generates with the image and video tools | Pick the best, approve |
| CurseForge and Modrinth pages, changelogs, translations | Writes them | Paste in, or let Claude fill the forms in a logged-in browser |
| GitHub repo and CI builds | Writes the workflow; can push if you attach the repository | Create the repo and grant access |

**Why not AI-generate in-game textures.** Image models blur pixel art and ignore the 16x16 grid, so generated tiles look muddy next to vanilla blocks. A scripted palette plus hand polish stays crisp and consistent.

**Audio.** Reuse pitched vanilla sounds in v1.0. If you add custom sounds, use only CC0 or properly licensed effects, and no carols or other copyrighted music.

**Fastest loop for you.** Claude writes a feature, pushes it, CI builds the jars, you drop them into a test instance and send back crash logs or screenshots. That keeps your time on playtesting, which is the part only you can do.

## Release plan and risks

Publish to CurseForge and Modrinth on the same day, submit each version as soon as its jars pass the checklist, and keep a fallback so a slow review cannot cost you Christmas.

**Release steps**

1. Check the name "Gingerbread Grove" and the mod id `gingerbread_grove` on both sites; change it now if either is taken.
2. Create both project pages as drafts in the first week, with icon, banner, description and at least four screenshots.
3. Upload one file per loader and version, four in total, named `gingerbread-grove-<loader>-<minecraft>-<version>.jar`, each tagged with the correct game version and loader.
4. Submit 1.21.1 by December 5 and 26.3 by December 12. New projects can sit in review for days, so do not wait for the second version.
5. Pick a licence before the first upload and state it on both pages. All textures, models and structures are original; no Mojang assets are copied.

**Risks and fallbacks**

| Risk | Fallback |
| --- | --- |
| The 26.3 port runs late | Ship 1.21.1 for Christmas and release 26.3 in January |
| CurseForge review is slow | Release on Modrinth the same day and link it from your channels |
| Entity renderers break on 26.3 | Keep renderers thin and in the version branch only |
| Worldgen bugs: floating trees, buried structures | Fly the test world in week 1, not in week 3 |
| Name or content clash | Use generic folk-tale and candy themes only; no licensed characters or songs |
| Scope creep | Freeze the feature list on November 30 |

**After launch.** Answer comments for the first week, then plan v1.1 for January: the boss at the Candy Cane Outpost, a real portal, and Overworld spawning if a worldgen library supports your versions.
